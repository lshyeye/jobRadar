# JobRadar · 岗位情报与匹配度看板 PRD

- **版本**：v1.1（2026-11-01，通用化 + 数据脱敏）
- **定位**：个人求职决策工具
- **状态**：已上线自用，v1.1 起对外可复用（数据源 / 画像可配置）

---

## 1. 背景与问题

已有采集脚本能完成「抓取 → 分类 → 统计 → 推送」，但存在三个问题：

1. **信息一次性消费**：推送看完即忘，几百条/期的 JD 无法回溯、对比、检索；
2. **无优先级判断**：原始岗位流没有回答求职者最关心的问题——「哪个最值得投」；
3. **不可复用也不可展示**：管线只是内部脚本，换一个人、换一个数据源就得重写。

## 2. 目标

| # | 目标 | 衡量方式 |
|---|------|---------|
| G1 | 岗位可回溯、可筛选、可检索 | 类型/公司/城市/关键词过滤，历史数据保留 |
| G2 | 每次采集完成后看板自动更新 | 管线产出新 JSON → 看板即最新 |
| G3 | 重点岗位给出匹配度建议 | 0–100 分 + 硬性要求/加分项/缺口 + 一句话建议 |
| G4 | **数据源与画像可替换** | 换数据源只改 `config/sources.json`，不改前端代码 |
| G5 | **数据可安全公开** | 脱敏脚本 + 残留校验，零真实公司名/链接入库 |

## 3. 非目标（Non-goals）

- ❌ 不做通用招聘平台（不面向其他求职者开放注册/账号体系）
- ❌ 不做投递状态管理闭环——列为 v2 候选
- ❌ 不做全量 JD 的 LLM 分析（成本控制，仅重点范围）
- ❌ 不做移动端 App（响应式 Web 即可）
- ❌ 不改动既有推送渠道的行为

## 4. 用户画像（可配置，示例）

- 一线城市 · 前端开发（React/TS），转型方向：AI Agent 应用工程师
- 核心诉求：从每期几百条 Agent 岗中快速识别「匹配我画像、值得投」的 Top 岗位
- 画像内容（技能分级、目标城市、权重、deal-breaker）写在 `config/profile.json`，
  规则通道按权重线性加权，LLM 通道把画像原文拼进 prompt

## 5. 用户故事

1. 打开看板即看到本期新增 JD 总数、三类岗位环比、公司分布（KPI + 图表），30 秒掌握市场动向。
2. 按「Agent 应用开发 + 城市 + 匹配度降序」筛选，直接得到本期最值得投的清单。
3. 点开一条岗位看到 JD 摘要、提取的硬性要求/加分项、匹配得分与理由，1 分钟内决策投/不投。
4. 换一个数据源或换一个求职者，只改配置、不改代码就能复用这套看板。

## 6. 功能范围

### 6.1 MVP（已实现）

| 模块 | 功能 | 数据源 |
|------|------|--------|
| 采集管线 | 多数据源归一化（公司/标题/城市/薪资/日期/链接/JD 正文） | 各招聘站公开接口 |
| LLM 分析 | 硬性要求/加分项提取 + 画像匹配打分 + 一句话建议 | 任意 OpenAI 兼容端点 |
| 规则兜底 | 技能词表命中 + 覆盖率加权 + 标题角色校准 | 本地词表 |
| 看板-KPI | 本期新增、三类岗位数与环比、公司集团分布 | stats.json |
| 看板-列表 | 岗位卡片流：筛选（类型/集团/城市/仅看已分析）+ 关键词搜索 + 匹配度排序 | stats.json + match_scores.json |
| 看板-详情 | 岗位抽屉：技能标签 + 分析结果 + 原始链接 | 同上 |
| 脱敏 | 公司名/链接/产品名替换 + 残留校验 | scripts/anonymize.py |
| 部署 | 静态托管，随时访问 | 静态产物 |

### 6.2 v2 候选（Backlog）

- 投递状态管理（Kanban：待投 → 已投 → 笔试 → 面试 → offer）
- JD 详情页正文展示（MVP 只有技能标签 + 分析结果，与用户预期有差距）
- 评测集与 precision@10（规则分 vs LLM 分同集对比）
- JD 历史趋势分析（某方向岗位发布趋势，判断扩缩编）
- 岗位去重（同岗多平台重复发布）

## 7. 指标

| 指标 | 类型 | 基线 | 目标 |
|------|------|------|------|
| 周打开次数 | 北极星 | 推送 2 次/周 | ≥ 3 次/周 |
| 筛选到「值得投」决策耗时 | 驱动 | 无工具 ~2 小时/周 | < 30 分钟/周 |
| 重点岗位分析覆盖率 | 健康 | 0 | ≥ 90% |
| 采集任务成功率 | 健康 | — | ≥ 95%（含凭据失效告警） |

## 8. 技术架构

```
[定时任务]
      │
      ▼
[采集管线] ──► stats.json ──► [看板 React+TS+Vite] ──► [静态部署]
      │
      ├──► [JD 正文库] ──► [匹配度分析：LLM 主 / 规则兜底] ──► match_scores.json
      │
      └──► [_picks.json] ──► 推送 / 周报
```

- **三份 JSON 契约**见 `docs/DATA_CONTRACT.md`，是替换数据源的唯一接口。
- 类型/接口统一收口在 `frontend/src/types/index.ts`，禁止函数内联定义。
- LLM 调用走 OpenAI 兼容端点，凭据只从环境变量读取（`LLM_API_KEY` / `LLM_BASE_URL`）。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 数据源反爬 / 凭据过期 | 分析覆盖不足 | 双通道传输 + 失败告警进周报；规则通道兜底 |
| LLM 成本与不可用 | 功能空窗 | 仅重点范围全量分析；失败重试上限 2 次；规则通道自动接管 |
| 真实数据外泄 | 合规风险 | 脱敏脚本 + `--verify` 残留校验；真实映射表 gitignore |
| 规则分与 LLM 分混排 | 排序失真 | 两套刻度不混排，清单只采信一种（见 TopPicks 策略） |
| 作品同质化 | 说服力弱 | 差异化点：真实规模数据 + 完整链路 + 脱敏工程化 |
