# JobRadar · 岗位情报与匹配度看板

> 把每周几百条岗位 JD 压缩成「这周该投哪几个」的排序清单。
> 采集 → 归一化 → 分类 → 画像匹配打分 → 看板，链路完整可跑，数据源可替换。

**它不是招聘网站，是给求职者自己用的决策工具。** 目标只有一个：
从打开看板到选定 3 个要投的岗位，把耗时从「逐条翻 JD 的两小时」压到十几分钟。

---

## 它解决什么问题

求职时真正的痛点不是「找不到岗位」，是**信息过载下的决策疲劳**：

- 招聘站每周新增几百条 JD，逐条看太贵，不看又怕错过；
- 推送看完即忘，第二周想回头找「上周那个挺合适的岗位」已经找不到；
- 最耗时的一步是**判断哪个值得投**，而不是获取岗位。

所以这个看板的北极星指标是「从打开到选定 3 个岗位的耗时」，不是「展示了多少条岗位」。

## 快速开始

```bash
# 看板（开发）——仓库自带演示数据，无需采集即可跑起来
cd frontend && npm install && npm run dev      # http://localhost:5199

# 看板（构建）
npm run build                                   # tsc 类型检查 + vite 构建

# Agent（没有 key 会自动用离线规划器）
python -m agent ask "北京 55 分以上的 Agent 岗有哪些"
python -m agent demo --offline                  # 跑一组示例，生成监控面板数据
python -m agent mcp                             # 启动 MCP server（stdio）

# 测试
python -m unittest discover -s tests -v
```

不需要 key、不需要网络、不需要外部服务：`data/` 里的 JSON 就是全部输入。

## 接自己的数据源

前端只认数据契约，不认数据来源。三步替换：

1. 复制 `config/sources.example.json` → `sources.json`，填你的 `listUrl` 与字段映射；
2. 采集器产出符合 [`docs/DATA_CONTRACT.md`](docs/DATA_CONTRACT.md) 的 `stats.json`；
3. 拷到 `frontend/public/data/`，刷新即用。

画像同理：`config/profile.example.json` 改成自己的技能、目标城市、权重即可——
规则通道按权重线性加权，LLM 通道把画像原文拼进 prompt。

## Agent 模块：让数据能被自然语言驱动

四个确定性工具（`search_jobs` / `get_job` / `market_stats` / `skill_gaps`）
挂在两条通道上：

| 通道 | 何时生效 | 特点 |
|------|---------|------|
| LLM（function calling） | 配了 `LLM_API_KEY` | 模型自己决定调哪个工具、调几次 |
| 离线规划器 | 没有 key，或模型调用失败 | 规则解析意图，确定、可复现、可单测 |

两条通道输出**同一套 trace**，所以监控面板不关心这次是谁干的：

```
python -m agent ask "..."  ──►  tools  ──►  data/agent_runs.json  ──►  AgentPanel
                                    ↑                                      │
                             MCP server（stdio）                    成功率 / P50·P95
                             任意客户端可调                         瀑布图 / 失败步骤
```

**为什么监控是重点而不是装饰**：Agent 的输出不可复现，唯一能做的是把每一次运行的每一步摊开
——调了哪个工具、花了多久、成功没有。没有这层观测，Agent 在面试和在生产里都是黑盒。
详见 [`docs/AGENT.md`](docs/AGENT.md)（含与目标 JD 的逐条对应表和诚实缺口）。

全部只用标准库：`urllib` 调兼容端点、自己实现工具循环、MCP server 是逐行 JSON-RPC。
不引 LangChain 的理由写在 AGENT.md 第一节——不是不爱用，是这个规模下它挡路。

## 技术栈

| 层 | 选型 | 说明 |
|----|------|------|
| 采集 | Python 3.13（仅标准库） | 零第三方依赖，受限网络里也能直接跑 |

## 关键设计决策

### 1. 不抓详情页 —— 列表接口里本来就有 JD 正文

最初预期「要啃反爬拿 JD 原文」，读代码后发现：多个招聘站的列表接口
**直接返回 JD 正文**（职责 + 任职要求），只是原管线抓完只留关键词标签、把正文扔了。

> 改造只是把已经在手的正文持久化，工作量从「几天」降到「半天」。
> 教训：动手前先读已有代码，别按想象评估工作量。

### 2. 以 URL 为键累积，正文库跨周只增不重抓

`jd_details.json` 用 URL 作主键累积合并，分析过的岗位永不重抓，增量友好、断点安全。
匹配度分析同样按 `jobId` 增量，中断后从断点续跑（每 10 条落盘一次）。

### 3. 匹配度分析做成双通道，而不是单点依赖

LLM 通道有外部依赖（key、配额、网络），一旦不可用不能让整个功能空窗：

| 通道 | 能力 | 何时生效 |
|------|------|---------|
| `llm_match` | 读 JD 原文，提取硬性要求/加分项、理解语义、给一句话投递建议 | 有有效 key 时优先 |
| `heuristic_match` | 技能词表命中 + 覆盖率加权 + 方向契合 + 城市/年限/短板 + **标题角色校准** | LLM 无产出时自动接管 |

两个通道输出**完全相同的 JSON 契约**，前端零改动；`model` 字段区分来源，
UI 也明确区分「LLM 深度分析」和「规则匹配分析（离线）」，不把规则分说成 LLM 分。

### 4. 规则通道踩的坑：分类器的 `type` 字段不可信

规则版第一版把「AI Agent 产品经理」打了 87 分、「IT 运维负责人」84 分。
根因是只看技术词命中，不看**岗位角色**。修法是加标题级校准（产品/运营/运维/算法研究/管理岗重罚）。

第二个坑更隐蔽：校准规则最初作用在**全文**上，于是 JD 里写「与产品经理协作」也会触发扣分——
均值被压到 35.9。改成**只匹配 `title` 字段**后，均值回到 42.0，分布才有区分度。

> 顺带发现采集侧的分类也有偏差（「医药数字营销项目经理」被标成前端），
> 所以评分必须自带角色校准，不能盲信上游分类。

### 5. 3D 星系要「有用」，不做纯装饰

914 条 JD 映射成三维粒子：Agent 岗橙色星团、前端蓝色、全栈绿色，
**已分析过的岗位粒子更大更亮**，hover 出岗位卡，点击直接开详情抽屉。
配色和位置承载数据语义，不是背景贴图。

### 6. 传输层双通道：urllib 主 + Node 回退

部分受限网络环境下，中间设备会重置 TLS 连接，导致 Python 请求失败而浏览器正常，
所以 HTTP 层做了**双实现**。这里踩过一个真 bug：回退通道最初没透传
`Authorization` 头，导致所有带认证的 POST 静默降级为匿名请求——
排查外部 API 报错时，先怀疑自己的传输层。

### 7. 拆包：three.js 单独成 chunk

主包 677KB → **158KB（gzip 52KB）**，three 拆出 518KB（gzip 130KB）。
three 极少随业务改动，独立 chunk 后可长期命中浏览器缓存。

## 数据脱敏

真实采集产物含公司名、产品名、游戏 IP 和岗位链接，**不能直接公开**。
`scripts/anonymize.py` 把它们改造成可公开的通用样本：

```bash
python scripts/anonymize.py --map config/pii_map.local.json --dry-run   # 只统计
python scripts/anonymize.py --map config/pii_map.local.json             # 落盘
python scripts/anonymize.py --map config/pii_map.local.json --verify    # 校验残留
```

| 维度 | 处理方式 |
|---|---|
| 公司名 / 数据源 | 替换为 `公司A`~`公司D` / `src_a`~`src_d` |
| 岗位链接 | 确定性哈希 → `https://jobs.example.com/<src>/<hash10>`，两侧 jobId 仍对得上 |
| 产品名 / 业务线 / 游戏 IP | 映射为通用业务域（例：某视频生成产品 → `视频生成`） |
| 个人画像痕迹 | 内部系统名 → 通用技术名词 |
| 城市 | 归一化（`Beijing` / `北京市` / `北京` → `北京`） |

三条设计约束：**映射表外置且不入库**（`pii_map.local.json` 已 gitignore）、
**替换幂等**（重复执行不二次哈希）、**可校验**（`--verify` 扫到任何残留即失败退出）。

## 已知限制

1. **演示数据只有 4 个数据源**，且链接指向 `example.com`（脱敏代价，点不到真实岗位）。
2. **规则通道不懂语义**：能判断「JD 要的技能你有没有」，判断不了团队背景、业务前景、
   隐性要求。分数的相对排序可信，绝对值参考意义有限。
3. **看板尚未在线部署**，目前是本地 dev server。
4. **采集器不在本仓库内**（见 `pipeline/README.md`），仓库尚不完整可复现。
5. **岗位去重未做**：同一岗位多平台发布会计两条。
6. **Agent 离线通道只认关键词**：没有 key 时由规则规划器兜底，理解不了「我适合转岗吗」这类
   语义问题；它的定位是「永远可用的降级」和「给 LLM 通道做对照」，不是替代。

## 非目标（Non-goals）

- **不做多用户产品**。单人工具，不做账号体系、权限、多租户。
- **不做全量岗位覆盖**。只接有公开接口的数据源，不为覆盖率去啃反爬。
- **不做简历自动投递**。自动投递涉及账号安全与平台规则，价值不匹配风险。
- **不用 LLM 编造岗位信息**。岗位数据全部来自真实接口，LLM 只做分析和排序，不做生成。
